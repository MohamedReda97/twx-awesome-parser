System purpose

Make a TWX application explain itself.

TWX Parser turns an opaque IBM Business Automation Workflow archive into a searchable object inventory, dependency model, and evidence-backed server-side code analysis report.

End-to-end processing

How a .twx becomes an architecture model.

The parser uses the archive conventions IBM BAW already produces. It does not execute process code and does not need a running BAW environment.

Drawing A — processing sequenceCalls inside one Node.js process
Drawing B — archive conventionsRead, not invented

Important fallbacks ZIP

The package manifest provides the canonical object list. For every entry, extraction first tries objects/<versionId>.xml, then falls back to objects/<id>.xml.

  • Missing or unsupported detailed parsers do not discard the object.
  • Toolkit objects are tagged by source and remain distinguishable from application objects.
  • Business Object references are resolved after the combined inventory exists.
The archive is the source of truth. The viewer never guesses an object type from its display name.
Object identification

Type detection starts with IBM metadata, then applies one explicit grouping rule.

PackageXmlParser reads each manifest object’s raw type. type-mappings.js translates it to a display name; detailed parsing remains type-specific.

Two separate concerns

Grouping decides where an object appears in the UI and output files. Detail extraction decides which fields, scripts, variables, schemas, or elements can be understood.

  • process → extractProcessDetails
  • coachView → extractCoachViewDetails
  • twClass → extractBusinessObjectDetails
  • bpd → extractBPDDetails

Other mapped types remain useful generic metadata objects rather than disappearing.

Static analysis

The analyzer narrows scope first, then proves what it can.

Only application-owned CSHS, Service, and BPD server-side scripts are eligible. HTML is excluded from JavaScript analysis, and toolkit declarations improve resolution accuracy.

Scope and engineering boundaries

What the result means—and what it does not claim.

The useful architectural property is explainability: every reported item should connect to an application element, a rule, and evidence. Heuristics remain explicitly separated from confirmed defects.

Designed to do

  • Parse IBM BAW TWX archive conventions locally.
  • Identify mapped object types and extract supported details.
  • Combine application and toolkit declarations for resolution.
  • Analyze application-owned server-side JavaScript for BAW 19, 20, 21, 23 and 24.
  • Produce evidence-backed findings and navigable JSON reports.

Deliberately not claiming

  • It does not execute processes or replace IBM runtime validation.
  • It does not analyze toolkit code as if it belonged to the application.
  • It does not treat HTML as JavaScript.
  • It does not label every heuristic as a confirmed bug.
  • It does not guarantee dynamic runtime behavior that static evidence cannot prove.
